# DECISIONS

Catatan keputusan teknis di luar / pelengkap `BACKEND_SPEC.md`.

| Tanggal | Keputusan | Alasan |
|---|---|---|
| 2026-10-17 | Memakai **Laravel 12** (12.70), bukan versi 13. | PHP yang terpasang di mesin pengembangan (XAMPP) adalah 8.2; Laravel 13 butuh PHP ≥ 8.3. Laravel 12 adalah versi stabil terbaru yang kompatibel. Bisa di-upgrade setelah PHP diperbarui. |
| 2026-10-17 | Prefix `/api/v1` diatur lewat `apiPrefix` di `bootstrap/app.php`, bukan `Route::prefix()` di `routes/api.php`. | Satu titik konfigurasi; semua route di `routes/api.php` otomatis ber-prefix `v1`. |
| 2026-10-17 | Origin CORS dibaca dari env `FRONTEND_URL` (boleh beberapa, dipisah koma), default `http://localhost:5173`. | Origin produksi bisa ditambah tanpa mengubah kode. `supports_credentials` tetap `false` karena auth memakai Bearer token, bukan cookie. |
| 2026-10-17 | Test berjalan di **SQLite in-memory** (`phpunit.xml`), aplikasi memakai MySQL (`.env`). | Test cepat dan tidak butuh server MySQL. Konsekuensi: hindari fitur SQL khusus MySQL di query; kalau terpaksa, tambahkan test terhadap MySQL. |
| 2026-10-17 | `knuckleswtf/scribe` dipasang sebagai dependensi **dev**. | Rekomendasi resmi Scribe; dokumentasi di-generate saat development (`php artisan scribe:generate`). Ditinjau ulang di Fase 10 bila `/docs` harus tersedia di server produksi. |
| 2026-10-17 | `APP_FALLBACK_LOCALE` tetap `en`. | Belum ada file terjemahan `lang/id`; pesan validasi Bahasa Indonesia akan ditambahkan di fase yang membutuhkannya. |
| 2026-10-17 | Tabel `users` tidak punya `name`, `email_verified_at`, `remember_token` (sesuai ERD). Model `User` men-set `$rememberTokenName = ''`. | Kolom mengikuti bagian 4 persis; auth memakai token Sanctum sehingga remember token tidak diperlukan. Tabel bawaan `password_reset_tokens` & `sessions` tetap dipertahankan karena dipakai framework. |
| 2026-10-17 | Selain default kolom di database, model juga mengisi `$attributes` untuk kolom status ber-default (mis. `talent.status_kandidat = tersedia`). | Supaya enum cast langsung terisi setelah `create()` tanpa perlu `refresh()`. |
| 2026-10-17 | Jumlah talent seeder = **20 termasuk** akun demo `talent@intellisys.test` (19 talent tambahan, email `talent01..19@intellisys.test`, password `password`). 14 profil lengkap + masuk pool, 6 belum lengkap. | Tafsiran paling sederhana dari "20 talent" di Fase 1. |
| 2026-10-17 | Seeder memakai `fake()->seed(2026)`. | Data acak (kompetensi talent) sama setiap `migrate:fresh --seed`, memudahkan demo dan pengecekan. |
| 2026-10-17 | Seeder berjalan dengan `WithoutModelEvents` dan mengisi `status_kelengkapan`, `talent_pool`, serta log progres `kebutuhan_dibuat` secara langsung. Indikator SLA log seed dihitung dengan versi sederhana R13 di `JobRequirementSeeder`. | Logika otomatis R4/R5 (Fase 3) dan Observer progres + R13 resmi (Fase 4) belum ada; data seed dibuat konsisten dengan aturan tersebut agar tidak dobel saat observer aktif. |
| 2026-10-17 | 5 job requirement seed diberi SLA bervariasi: 2 `aman`, 1 `mendekati`, 1 `terlambat` (status `diajukan`), dan 1 `draft`. | Memberi data untuk demo indikator SLA dan pengingat scheduler. |
| 2026-10-17 | Registrasi talent & HR Client langsung mengembalikan token + user (201), sama seperti login. | Pengguna tidak perlu login ulang setelah daftar; format response sama dengan login sehingga mudah dipakai frontend. |
| 2026-10-17 | Registrasi HR Client **selalu membuat klien baru**, meskipun nama perusahaan sudah ada. Bergabung ke klien yang sudah ada belum didukung. | Sesuai R1. Penggabungan klien ganda (atau undangan HR ke klien yang sudah ada) bisa dibuat nanti lewat endpoint internal. |
| 2026-10-17 | Login gagal (email tidak terdaftar atau password salah) dibalas **422** dengan pesan sama: "Email atau password salah." Status nonaktif (403) hanya dicek setelah password benar. | Pola standar Laravel (ValidationException); pesan yang sama mencegah penebakan email terdaftar, dan status akun tidak bocor ke orang yang tidak tahu password. |
| 2026-10-17 | Endpoint auth publik (register, login) dibatasi **10 request/menit per IP** (`throttle:10,1`). | Mengurangi risiko brute force password. |
| 2026-10-17 | Menonaktifkan akun langsung **menghapus semua token** akun tersebut. | R3 hanya menyebut penolakan login; tanpa pencabutan token, user nonaktif masih bisa memakai sesi lama. |
| 2026-10-17 | Manager **tidak bisa mengubah status akunnya sendiri** (403). | Mencegah sistem kehilangan semua Manager aktif secara tidak sengaja. |
| 2026-10-17 | `PUT /pegawai/{id}` bersifat parsial (kolom `sometimes`) dan juga bisa mengubah email, password, dan role akun (terbatas role internal). | Satu endpoint kelola akun internal sesuai tabel endpoint; tidak perlu endpoint terpisah untuk ganti password pegawai. |
| 2026-10-17 | Helper profil di `User` memakai nama relasi `talent()`, `hrClient()`, `pegawai()` ditambah `profil()`, `isInternal()`, `hasRole()`, `idKlien()`; tidak membuat `talentProfile()` dkk. | Relasi Eloquent sudah berfungsi sebagai helper profil; nama tambahan hanya duplikasi. |
| 2026-10-17 | Role dicek dua lapis: middleware `role:` (lapis route) **dan** Policy (lapis data, mis. `UserPolicy::updateStatus`). FormRequest memakai `Gate::inspect()` agar pesan penolakan dari Policy sampai ke client. | Sesuai bagian 2 & 5 spec; `bool` di `authorize()` membuang pesan Policy. |
| 2026-10-17 | Semua error API dibalas JSON berbahasa Indonesia (401, 403, 404, 429) lewat `bootstrap/app.php`, ditambah `lang/id/validation.php` untuk pesan validasi. Guest tidak di-redirect ke route `login`. | Aturan 6 spec (pesan ke pengguna dalam Bahasa Indonesia); API tidak punya halaman login. |
| 2026-10-17 | `TalentResource` menampilkan `ada_cv` (boolean), bukan path `file_cv`. | Path file ada di disk private; CV diunduh lewat endpoint terproteksi (Fase 3). |
| 2026-10-18 | Repo dipisah: `Capstone_Kelompok14` menjadi repo **khusus backend** (isi `backend/` dipindah ke root repo dengan riwayat tetap tersambung); frontend pindah ke repo baru yang dimulai dari satu commit. | Keputusan tim agar backend dan frontend dikelola terpisah. Panduan pindah untuk yang sudah clone ada di `SETUP.md`. |
| 2026-10-21 | Skema tambahan SCRUM-8 **dipertahankan**: 13 kolom profil di `talent` (`tanggal_lahir`, `nomor_telepon`, `alamat`, `domisili`, `tentang_saya`, `nama_institusi`, `jurusan`, `tahun_lulus`, `gaji_harapan`, `linkedin`, `instagram`, `github`, `portfolio`) dan tabel `riwayat_pendidikan`, `pengalaman_kerja_talent`, `sertifikat_talent`, `bahasa`, `talent_bahasa`. Didokumentasikan di BACKEND_SPEC 4.2 ("Profil talent") dan bagian 11. | Dibutuhkan untuk profil & CV yang rinci (FR-03, FR-04) dan sudah ter-merge ke main. Keputusan tim, bukan bagian ERD awal; ERD di laporan perlu diperbarui. |
| 2026-10-21 | **R4 diubah:** profil lengkap = `nama_lengkap` terisi + minimal 1 `riwayat_pendidikan` + minimal 1 kompetensi. Kolom teks `pendidikan` dan `pengalaman_kerja` tidak lagi menjadi syarat. Status bisa turun lagi ke `belum_lengkap`; entri talent pool yang sudah ada tidak dihapus (R5 hanya menambah). | Riwayat pendidikan terstruktur menggantikan kolom teks bebas sebagai sumber data CV. |
| 2026-10-21 | `PUT /talent/profil` menerima `riwayat_pendidikan[]` dan `riwayat_pengalaman_kerja[]`; jika dikirim, **seluruh daftar lama diganti** (id baris ikut berganti); jika tidak dikirim, daftar lama tetap. `PUT /talent/profil/kompetensi` boleh mengirim `[]` untuk mengosongkan kompetensi. | Tanpa jalur ini riwayat pendidikan tidak bisa diisi lewat API sehingga R4 tidak pernah tercapai. Pola "ganti semua" paling sederhana untuk form profil di frontend; endpoint CRUD per baris bisa ditambah nanti. Sertifikat & bahasa belum punya jalur isi. |
| 2026-10-21 | Path endpoint talent mengikuti spec: `/talent/profil` dan `/talent/profil/kompetensi` (sebelumnya `/talent/profile` dan `/talent/kompetensi`), dengan middleware `role:talent`. FormRequest talent tidak lagi memakai `authorize()` bool. | Spec bagian 7 adalah sumber kebenaran; role dicek di route agar role lain mendapat 403 dengan pesan Indonesia yang sama seperti endpoint lain. |
| 2026-10-21 | **R6:** CV disimpan di disk private (`local`, `storage/app/private/cv/talent-{id}.pdf`), bukan disk `public`. Generate ulang menimpa file dan memperbarui record `dokumen` jenis `cv` yang sama (satu record CV per talent). Generate ditolak 422 jika profil belum lengkap. Response tidak memuat path file. | CV berisi data pribadi; disk `public` bisa diakses siapa saja lewat `/storage`. Sesuai keputusan 2026-10-17 bahwa path tidak dikirim ke client. |
| 2026-10-21 | **R9 diubah:** `skor_kecocokan = 0,8 × skor_kompetensi + 0,2 × skor_pengalaman`. Lama pengalaman dihitung dari `pengalaman_kerja_talent` (periode tumpang tindih digabung, `masih_bekerja` dihitung sampai hari ini); skor pengalaman = 100 jika ≥ `pengalaman_min`, selain itu proporsional. Kandidat tetap wajib `skor_kompetensi` > 0. | Memakai `pengalaman_min` job requirement yang sebelumnya diabaikan, tanpa kolom baru. Syarat kompetensi > 0 mencegah talent yang tidak cocok sama sekali muncul hanya karena pengalaman. |
| 2026-10-21 | R5 dipindah dari `TalentService` ke `TalentObserver` (event `updated` saja, `TalentPool::firstOrCreate`). Seeder tetap mengisi `talent_pool` sendiri, kini dengan `updateOrCreate`. | Satu tempat untuk R5 apa pun jalur perubahan statusnya. Talent baru selalu `belum_lengkap`, jadi event `created` tidak perlu; seeder membuat talent lengkap lewat `create` (tidak memicu `updated`) dan aman walau dijalankan dengan model event aktif. |
| 2026-10-21 | Talent pool tidak punya endpoint tambah; "tambah kandidat" (SCRUM-65/66) terjadi otomatis lewat R5. TS mengelola entri lewat `PATCH /talent-pool/{id}` (`status_ketersediaan`, `tag_keahlian`). | Sesuai spec bagian 7; data kandidat diisi talent sendiri lewat profil. |
| 2026-10-21 | `talent.pendidikan` di response talent pool = riwayat pendidikan terbaru dengan format "S1 Informatika – Telkom University" (yang `tahun_selesai`-nya kosong dianggap paling baru); fallback ke kolom teks `talent.pendidikan`. Detail memakai `riwayat_pengalaman_kerja` + `lama_pengalaman_tahun` (1 desimal), bukan teks `pengalaman_kerja`. | Data terstruktur lebih berguna untuk TS; perhitungan lama pengalaman sama dengan R9 (`PengalamanKerjaService`). |
| 2026-10-21 | Filter `kompetensi[]` di `GET /talent-pool` memakai logika **DAN** (talent harus punya semua kompetensi yang dipilih). | Pencarian kandidat biasanya mempersempit hasil per skill tambahan. |
| 2026-10-21 | Unduh CV: `GET /talent/cv/download` (talent, miliknya) dan `GET /talent-pool/{id}/cv` (internal). 404 dengan pesan khusus lewat `DataTidakDitemukanException`; `NotFoundHttpException` lain tetap "Data tidak ditemukan.". | Pesan 404 bawaan route model binding berisi nama class model; pesan khusus hanya untuk exception yang sengaja dilempar. |
| 2026-10-21 | `GET /kompetensi` (semua role, read-only) dipaginasi seperti list lain (default 15, maks 100) dengan `search` dan `kategori`. Kelola master (POST/PUT/DELETE) belum dibuat. | Konsisten dengan aturan list; frontend bisa memakai `per_page=100` untuk dropdown. |
| 2026-10-21 | **Fase 4:** endpoint baru di luar spec `GET /klien` (internal, read-only, `search`, paginate). | AM wajib memilih `id_klien` saat membuat job requirement (R7), tetapi belum ada cara mengambil daftar klien. |
| 2026-10-21 | Job requirement: HR Client membuat job → `id_am` null (belum ada AM penanggung jawab); AM membuat → `id_am` = dirinya. `id_klien` yang dikirim HR Client diabaikan (selalu kliennya), begitu juga filter `id_klien`. Klien tidak bisa diganti lewat PUT. | Tafsiran paling sederhana R7; penugasan AM untuk job buatan HR Client bisa ditambah nanti. |
| 2026-10-21 | Transisi status job requirement lewat `PATCH /status` hanya `draft → diajukan` (deadline harus belum lewat) dan `draft/diajukan/diproses → dibatalkan`. `diproses` diisi otomatis oleh R10, `terpenuhi` oleh R19 (Fase 5). Membatalkan job mengembalikan talent `dalam_proses` yang screening-nya untuk job ini belum `tidak_lolos` menjadi `tersedia`. | Talent tidak boleh tertahan "dalam proses" untuk job yang sudah dibatalkan; talent hanya bisa diproses di 1 job sekaligus karena rekomendasi/screening mensyaratkan `status_kandidat = tersedia`. |
| 2026-10-21 | **R13:** job `dibatalkan` diperlakukan sama dengan `terpenuhi` (selalu `aman`, tidak pernah `terlambat`/`mendekati`). "Sisa ≤ 3 hari" dihitung dengan waktu (deadline ≤ sekarang + 72 jam), bukan pembulatan hari. | Job yang dibatalkan tidak perlu dipantau SLA-nya. Seeder kini memakai `ProgresService::indikatorSla` (versi sederhana di seeder dihapus). |
| 2026-10-21 | **R9:** `lama_pengalaman` dibulatkan 1 desimal sebelum dihitung ke `skor_pengalaman`. | Tanpa itu contoh spec (Jan–Des 2023 = 364 hari) menghasilkan 69,97, bukan 70; skor kini konsisten dengan lama pengalaman yang ditampilkan ke TS. |
| 2026-10-21 | Screening: dibuat selalu `pending` (hasil diubah lewat PUT). Hasil `tidak_lolos` final (tidak bisa diubah lagi), karena talent sudah dilepas dan mungkin diproses di job lain. Screening tidak bisa diubah jika sudah punya pengajuan atau job-nya terpenuhi/dibatalkan. Rekomendasi & screening hanya untuk job `diajukan`/`diproses`. | Mencegah status talent tidak konsisten (R10/R11). |
| 2026-10-21 | R8 dan R12 (bagian screening) diimplementasikan di `JobRequirementObserver` dan `ScreeningTalentObserver`; log memakai `ProgresService::catat`. `penanggung_jawab` log = AM job (kebutuhan_dibuat) atau TS yang menyaring (screening/ditolak). Seeder (model event mati) mencatat log langsung dengan service yang sama; `ScreeningSeeder` membuat 3 screening demo (lolos, pending, tidak lolos) untuk job Backend Developer. | Satu tempat untuk log progres apa pun jalurnya; data demo konsisten dengan R9–R12. |
| 2026-10-21 | `GET /job-requirements` punya `meta.ringkasan` (jumlah per status + `sla_terlambat`, `sla_mendekati`) seperti talent pool; `GET /job-requirements/{id}/progres` mengembalikan data job + `log_progres`; `GET /progres` mengembalikan daftar job + `progres_terakhir` + `jumlah_screening`. | Kartu ringkasan dan tabel monitoring di frontend tanpa request tambahan. |
